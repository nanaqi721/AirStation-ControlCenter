# 虚拟空压机仿真实现指南

## 1. 文档用途

在没有真实空压机、PLC 或仪表时，按本文逐步建立可重复的空压站行为模型，用于验证：

- 上位机实时画面、状态动画、报警、趋势、历史数据和报表。
- 参数写入、控制命令、权限、写后回读和操作审计。
- 空压机、储气罐、管网和辅机之间的状态与数值关系。
- 高温、超压、用气变化、设备故障等业务异常路径。

本文是仿真功能的单一事实来源。[AGENTS.md](../AGENTS.md) 只保留进入本文的条件，不复制这里的实现细节。仿真点表和参数都是开发样例；接入真实设备时，以设备手册和现场确认点表为准。

虚拟串口、Modbus Slave、NModbus 主站/从站、地址、轮询、超时和重连由 [MODBUS_COMMUNICATION_IMPLEMENTATION.md](MODBUS_COMMUNICATION_IMPLEMENTATION.md) 维护。

## 2. 最终目标

最终形成两个独立程序：

```text
AirCompressor.ControlCenter.WinForms    AirCompressor.ControlCenter.Simulator
上位机，NModbus RTU 主站                虚拟空压站，NModbus RTU 从站
          │                                  │
        COM8  ←────── 虚拟串口对 ──────→   COM9
```

虚拟空压机必须能够：

- 响应上位机的 Modbus 读取和允许的写入请求。
- 自动生成压力、温度、电流、运行时间和状态。
- 执行停止、启动、加载、卸载、停机和故障状态转换。
- 根据阈值触发与恢复报警。
- 接受人工故障注入和通信异常注入。
- 使用确定性随机种子或固定场景，使问题可以重复验证。

## 3. 实现范围分期

三个阶段是项目仿真范围的权威定义。完成当前阶段的模型、界面、点表和验证标准后，再进入下一阶段。

### 第一阶段：最小闭环

只模拟：

- 1 台空压机。
- 1 个公共储气罐。
- 总管压力。
- 压力、温度和电流。
- 启动、停止、加载和卸载。
- 1 个高温报警。
- 车间用气量。

储气罐把空压机供气量、车间用气量和总管压力连接成第一个完整闭环。第一阶段不加入冷却塔、水泵和多机调度。

完成标准：改变车间用气量会引起总管压力变化；空压机根据压力完成加载/卸载；启停、温度和高温报警可重复验证。

### 第二阶段：多机集控

在第一阶段基础上扩展：

- 4 台空压机。
- 公共储气罐和分汽缸。
- 多机轮换。
- 加载/卸载协调。
- 主机、辅机和备用机。
- 运行时间均衡。
- 故障后自动切换备用机。

完成标准：不同用气负荷下能够自动决定运行台数；轮换和故障切换不会造成重复启动或压力失控；每次调度有原因和记录。

### 第三阶段：辅机系统

在第二阶段基础上增加：

- 冷却塔。
- 两台冷却水泵。
- 过滤器压差。
- 储气罐排水阀。
- 管路电动阀。
- 冷却水温度和液位。
- 辅机报警与联锁。

完成标准：空压机热负荷会影响冷却系统；水泵和冷却塔具有运行、备用和故障状态；过滤器、阀门和液位报警能够触发、恢复并在上位机中追溯。

## 4. 仿真架构与通信边界

### 4.1 通信验证

通信按两步实施：先使用 Modbus Slave 软件手工验证基础通信，再使用独立 C# 模拟器中的 NModbus 从站承载动态空压站数据。具体步骤和完成标准统一查阅 [MODBUS_COMMUNICATION_IMPLEMENTATION.md](MODBUS_COMMUNICATION_IMPLEMENTATION.md)。

Modbus Slave 只验证寄存器读写，不承担空压机、储气罐和辅机行为模型。

### 4.2 应用内模拟网关

在上位机基础设施层实现与真实网关相同接口的 `SimulatedPlantGateway`：

```text
IPlantGateway
├── NModbusPlantGateway       真实串口通信
└── SimulatedPlantGateway     内存数据，无串口
```

它用于快速开发界面、报警、历史记录和报表，不经过串口，也不能证明 RTU 通信链路正确。通过配置选择网关实现，不在 UI 中到处编写“如果是模拟模式”的分支。

完成标准：切换配置即可在真实网关与模拟网关之间运行；应用层和 UI 不需要修改。

### 4.3 独立虚拟空压站

建立独立的 `AirCompressor.Simulator` 程序，通过 NModbus 创建 RTU 从站网络和从站数据区。该程序经过虚拟串口与上位机通信，能够同时验证空压机行为和完整 RTU 链路。

具体通信 API、串口配置和验证步骤由 [MODBUS_COMMUNICATION_IMPLEMENTATION.md](MODBUS_COMMUNICATION_IMPLEMENTATION.md) 维护。

完成标准：模拟器和上位机分别运行，完整执行启动、加载、卸载、报警、复位和停机流程；重新启动任一程序后可以恢复通信。

## 5. 仿真模型实施顺序

### 阶段 A：确定仿真点表

第一阶段统一使用 [空压站PLC学习用Modbus变量表.xlsx](../空压站PLC学习用Modbus变量表.xlsx)，不在模拟器代码或本文中重新定义地址。表中的冷却泵、过滤器和排水阀点位用于后续辅机练习；第一阶段只启用最小闭环所需点位，其余保持默认或未启用状态。

1. 从权威点表中选出当前阶段需要启用的点位。
2. 按表中的数据区、协议偏移、数据类型、缩放、单位和读写权限建立映射。
3. 按表中的枚举、场景和推荐读取块执行人工复核。
4. 扩展点位时先版本化点表，再修改模拟器和主站配置。

完成标准：形成一份无地址冲突、可以被程序读取的最小点表，并通过人工复核。

### 阶段 B：完成通信验证

按 [MODBUS_COMMUNICATION_IMPLEMENTATION.md](MODBUS_COMMUNICATION_IMPLEMENTATION.md) 完成 Modbus Slave 手工验证和独立 NModbus 从站的基础读写。本文从通信已能稳定传输寄存器数据的前提继续实现设备行为。

完成标准：通信文档中当前阶段的全部适用验证项通过并已记录。

### 阶段 C：建立模拟器项目

在用户明确要求写入后，创建独立项目，例如：

```text
src/
├── AirCompressor.ControlCenter.WinForms/
└── AirCompressor.ControlCenter.Simulator/
```

模拟器内部建议分为：

```text
SimulatorHost
├── SimulationEngine          时间推进与状态机
├── AirCompressorModel        当前物理量、状态、设定值
├── RegisterMap               模型与 Modbus 地址映射
├── ModbusSlaveHost           NModbus RTU 从站生命周期
├── ScenarioController        正常、报警、断线等场景
└── Diagnostics               请求、写入、错误和状态日志
```

先做控制台程序即可，不要先投入大量时间制作模拟器界面。需要人工控制场景时，再增加简单 WinForms 面板。

完成标准：模拟器可以从配置读取串口参数，启动和停止从站，退出时释放串口，并能显示当前状态和通信错误。

### 阶段 D：实现空压机状态机

第一版状态：

```text
Stopped  --启动命令--> Starting --启动延时完成--> Loading
Loading  --达到卸载压力--> Unloading
Unloading --降到加载压力--> Loading
任意运行状态 --停机命令--> Stopping --停机完成--> Stopped
任意状态 --严重故障--> Fault
Fault --故障条件消失且收到复位--> Stopped
```

建议约束：

- 停止状态收到停止命令保持停止，不重复产生事件。
- 故障未消除时拒绝复位，并返回可诊断的结果。
- 启动和停机设置短暂过渡时间，便于验证 UI 状态。
- 控制命令使用上升沿或命令序号，避免轮询期间重复执行。
- 每次状态转换记录时间、来源和原因。

完成标准：所有允许的状态转换均能执行；不允许的转换不会改变状态，并留下诊断记录。

### 阶段 E：生成动态数据

使用固定更新周期和实际经过时间 `dt` 推进模型，不让数据变化依赖 UI 刷新速度。第一版可以每 200 ms 更新内部模型，上位机按自身轮询周期读取。

建议规律：

| 状态 | 压力 | 温度 | 电流 | 运行时间 |
|---|---|---|---|---|
| Stopped | 缓慢降至残余压力 | 逐渐接近环境温度 | 0 | 不增加 |
| Starting | 小幅升高 | 开始升高 | 启动电流短时偏高 | 增加 |
| Loading | 持续升高 | 接近加载目标温度 | 接近加载电流 | 增加 |
| Unloading | 缓慢下降 | 稳定或小幅下降 | 降至卸载电流 | 增加 |
| Stopping | 缓慢下降 | 开始冷却 | 逐渐归零 | 视设备定义决定 |
| Fault | 按故障类型处理 | 可能保持异常 | 通常归零 | 不增加或另行定义 |

第一版示例范围：

```text
加载压力下限：0.60 MPa
卸载压力上限：0.75 MPa
运行温度：65～85 ℃
高温报警：95 ℃
加载电流：额定值附近小幅波动
卸载电流：显著低于加载电流
```

为避免锯齿和不真实跳变，可采用“向目标值渐近”的形式：

```text
新值 = 当前值 + (目标值 - 当前值) × 响应系数 × dt
```

随机噪声只用于小幅波动，使用可配置种子；自动化测试时固定种子，人工演示时可随机。

完成标准：数值连续、范围合理、状态变化与数值方向一致，同一测试场景可以重复。

### 阶段 F：映射到 Modbus 数据区

按权威点表建立 `RegisterMap`，并保持“模型字段—点表标签—协议地址”一一对应。表中的文档地址供人阅读，NModbus 调用使用协议偏移；32 位值按点表指定的寄存器数量与字序编码。若真实设备的数据区或地址规则不同，应替换点表和映射，不为保持当前学习表而强行改造现场协议。

完成标准：每个模型字段只有一个明确地址映射；32 位值和浮点值有明确字序；写入越界值会被拒绝或按设备约定返回异常。

### 阶段 G：处理上位机写入

模拟器收到写入后不能只修改寄存器，还要把命令交给状态机：

```text
Modbus 写入
  ↓
地址和功能码校验
  ↓
读写权限与范围校验
  ↓
转换为领域命令或设定值
  ↓
状态机执行
  ↓
更新数据区并供上位机回读
```

控制命令建议执行一次后自动清零，或者使用递增命令序号；最终行为应与真实设备协议一致。参数写入要验证上下限和相互关系，例如加载压力必须低于卸载压力。

完成标准：合法写入改变模型且回读一致；非法地址、只读点和越界数值不会改变模型，并产生明确结果。

### 阶段 H：报警与故障注入

第一版报警字示例：

| Bit | 报警 |
|---:|---|
| 0 | 排气温度高 |
| 1 | 排气压力高 |
| 2 | 电机过载 |
| 3 | 油滤堵塞 |
| 4 | 急停 |

报警至少包含“产生时间、当前是否存在、恢复时间、是否需要复位”。为测试上位机，可提供这些可控场景：

- 强制高温和恢复。
- 强制超压和恢复。
- 同时激活多个报警位。
- 暂停响应，模拟超时。
- 关闭串口，模拟断线。
- 返回超量程值或保持旧值，验证 Bad/Stale 数据质量。
- 高频切换故障位，验证报警去抖。
- 拒绝特定写入，验证上位机错误提示。

完成标准：每个异常场景都能人工触发、恢复并重复；上位机能区分设备报警、通信异常和数据质量异常。

### 阶段 I：验证与自动化

按以下顺序验证：

1. 模型单元测试：状态转换、数值范围和报警阈值。
2. 映射测试：模型值与寄存器原始值双向转换。
3. 从站集成测试：NModbus 主站读取和写入模拟从站。
4. 应用集成测试：UI、报警、历史数据和操作日志。
5. 异常测试：超时、断线、重连、非法数据和重复命令。
6. 长时间运行：至少覆盖数据库归档和多次重连。

每个测试场景记录初始条件、操作、预期值和实际值。固定时间源或提供“单步推进”能力，可避免自动化测试依赖真实等待。

完成标准：正常和异常场景均有可重复的验证记录；失败能够定位到模型、映射、通信或 UI 层。

## 6. 分期交付规则

- 第一阶段是当前 MVP；在其完成标准全部通过前，不实现多机调度或辅机联锁。
- 第二、三阶段只在前一阶段已经验证且 [PROJECT_STATUS.md](PROJECT_STATUS.md) 已记录后开始。
- 每次只增加一个可验证行为，例如“用气量上升导致压力下降”，再扩展下一项。
- 模拟器界面服务于场景控制和诊断，不先于模型正确性开发。

## 7. 常见问题

### 通信类问题

地址偏移、串口占用、参数不一致、超时和重连统一查阅 [MODBUS_COMMUNICATION_IMPLEMENTATION.md](MODBUS_COMMUNICATION_IMPLEMENTATION.md)。

### 数值跳变或不真实

将状态机与数据生成分开，使用 `dt` 和目标值渐近算法；限制随机噪声幅度，不要每次轮询直接生成完全随机值。

### 命令重复执行

轮询和线圈保持可能导致同一命令被多次看到。使用上升沿、自动清零或命令序号，并记录最后处理的命令。

### 模拟通过但现场失败

内存模拟只验证业务逻辑；独立 RTU 从站才能覆盖串口链路；真实设备还会带来实际时序、厂商地址规则和异常响应。三层测试不能互相替代。
